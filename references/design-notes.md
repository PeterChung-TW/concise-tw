# 設計取捨記錄（為什麼三條要修正、一條要拆半）

> 本 skill 的規則骨架參考 ayghri/i-have-adhd 的十條，但以下四處刻意不照原樣。
> 這些修正全部來自真實工程 session 的實測，不是紙上推演。

## 修正一：時間估計（原 Rule 6）

原版要求「一律給具體分鐘數」。問題：**語言模型沒有時間感**——對它是一個回合的事，
對使用者可能是好幾分鐘的空等；它估「5 分鐘」和估「30 分鐘」的依據其實是同一種感覺，
也就是沒有依據。實際用下來，「AI 憑感覺報時間」是我抓到次數最多的問題之一。

修正版：**只講可驗證的事實**，例如「這批要跑 45 頁、上次同樣的量花了 19.8 分鐘」，
讓人自己換算，比一個編出來的數字誠實得多。

通用原則：凡是判準的輸入是「AI 的主觀感受」（快不快、久不久、難不難），
就該換成外部可驗證的事實。

## 修正二：清單上限（原 Rule 9）

原版要求超過五項就拆「立即／稍後」。問題：稽核、審查、盤點類工作的價值
恰恰在**完整枚舉**：一份 41 條的稽核清單硬拆成 5+36，後面 36 條實務上就是消失了。

修正版：**分層**。摘要層最多 5 項（人眼掃得完），明細層不設上限、寫進檔案並指路。
上限約束的是「一次塞給人看多少」，不是「總共處理多少」。

## 修正三：岔題處理（原 Rule 4）

原版要「壓制岔題」。問題：工程 session 裡的岔題常常是真問題的第一個訊號——
壓掉它，問題會在更貴的時機回來。但反過來「當場即興處理岔題」也不對，主線會失焦。

修正版：**記錄，不處理**。岔題不進主線敘事、不即興動手，收尾用一行帶出
（「另發現 X，已記待辦」）。壓制與即興都是錯，記錄才是對的第三條路。

## 拆半：無總結（原 Rule 10）

原版要「無開場白、無總結」。前半吸收：開場白與客套結語是純噪音，砍。
後半拒絕：**「無總結」只適合面對面即時對話**。實務上我自己常常是事後才看訊息的
（通知、聊天視窗、回頭翻），完全沒有收尾等於什麼都看不到。

拆半版：收尾保留但壓縮成三句——改了什麼／怎麼驗的／使用者下一步。三件事三句話，不鋪陳。

## 為什麼是純 Markdown、零 hook

原版以 plugin 形式安裝。本 skill 刻意採純規則檔路線：

1. **可審計**：純規則檔，裝之前整份看得完；沒有「今天乾淨、明天更新後不保證」的 hook 執行面。
2. **可攜**：不依賴 hook 的環境（企業政策鎖 hooks 的機器、其他支援 skill 的工具）一樣能用。
3. **可退**：刪資料夾＝完全移除，不留旗標檔、不留設定殘骸。

代價是「長 session 後模型可能漂回囉唆」——那時再說一次「精簡」即可。
我的取捨是：「使用者說一聲」比「靠 hook 每回合自動塞規則」便宜，也比較不打擾。
